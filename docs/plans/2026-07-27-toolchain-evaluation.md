# Toolchain evaluation: should the architecture be rebuilt?

Deep-research evaluation of alternative toolchains for every stage of the pipeline (source ingestion, mosaic, raster and vector cartographic products, packaging, deployment), prompted by: full-planet rebuilds on every change, the PR #83 bbox build running 18+ hours, and per-tile Worker compute at serve time. Ten research passes fed this: a repo audit with measured numbers, and web-verified surveys of PostGIS/Martin (vector and raster), Planetiler/Tilemaker/Rust tooling, PMTiles merge/serving economics (with live measurements), mosaic storage formats (Zarr/Icechunk, TileDB, COG+GTI), dynamic raster tiling, and planet-scale precedents.

## Headline

**The architecture is not wrong. The cost is concentrated in exactly one stage, and every serious alternative reconstructs what this repo already has.**

The measured evidence (from this repo's own docs and logs):

- The measured planet build was 11h19m; **7h01m (62%) was two serial tippecanoe/tile-join invocations**. A zero-change incremental build was 8h12m, of which **7h31m was the serial vector-bundle chain on a >90%-idle 48-core box**.
- In the live PR #83 run, **609 of 613 DAG steps finished in 5h02m**; the single remaining job — the planet-wide `--generate-variable-depth-tile-pyramid` walk, which tippecanoe executes with **one worker thread** — ran alone for 13+ hours. The cell-sharded fix (`b077795`) landed after that run was dispatched and is not in it.
- Everything else already works: terrain rendered the planet at 31 avg cores in 2h36m; 239 overlay bundles rebuild in ~2 minutes; the mosaic is per-tile COGs with content-addressed publish and tile-granular staleness.
- ~¾ of the depare archive bytes are inland OSM nodata polygons carried at full coastline detail through nine zoom levels; pre-simplifying them to stem resolution measured −54% to −67% of vertices. **Content volume, not tiling speed, is the biggest single lever.**

Precedent is unanimous on the two big questions. Every planet tileset builder uses **one big machine** (Mapterhorn: 32 cores, Protomaps: one c7gd.8xlarge-class box, osm.org: one 8-core/128 GB box) — the fork is only whether you make the full rebuild fast (Protomaps: 3 h, rebuild daily) or make the work incremental (Mapterhorn: hash the per-macrotile work plan, skip unchanged items). And every planet terrain/tile server **pre-bakes and serves static tiles from object storage behind a thin edge layer** — nobody serves planet terrain or complex low-zoom polygons dynamically.

## The PostGIS + Martin question, answered directly

**Mosaic in PostGIS raster: no.** The extension is maintained (active 2026 commits) but adoption has collapsed — 142 lifetime GIS StackExchange questions, zero in 2026, and no production planet-scale DEM deployment found anywhere. PostGIS's own workshop: rasters are "built for analysis, not for generating pretty pictures." In-db Float32 would be ~2–4× the COG bytes with TOAST detoast on every read; out-db requires enabling GDAL drivers that give any SQL role arbitrary file read + SSRF from the DB host, and is functionally "a tile index in Postgres over your COGs" — which the GeoParquet/GTI index already is, with no database. Crunchy Data's own guidance collapses to the same shape (pixels in object storage, index elsewhere).

**Martin serving vector tiles on the fly: no, and its flagship agrees.** Martin is the clear 2026 leader of the PostGIS tile servers (active MapLibre-org project; tegola/pg_tileserv/t-rex are stale or dead), and it genuinely beats tippecanoe on per-feature zoom gating (`WHERE minzoom <= z`) and the ft/m ladder (`WHERE sys = ...`). But: there is no equivalent of `--drop-densest-as-needed` anywhere in the ecosystem — nothing measures a tile and drops features to fit a byte budget; per-tile `ST_Simplify` produces seams and slivers on shared depare edges (osm.org's PoC disabled simplification entirely to stop coastline artifacts); and the one true planet-scale deployment — openstreetmap.org on Tilekiln + PostGIS since July 2025 — **does not serve on the fly**: it pre-renders z0–12 (~a day) and serves from a storage tier. Tilekiln's own README says systems updating less than minutely should use Planetiler or Tilemaker instead. This project refreshes weekly. Estimated planet DB: 1–2 TB (global 10 m contours alone measured ~500 GB in PostGIS) on an always-on 128–256 GB-RAM box, versus ~$6/month today. Martin's raster/COG source can't serve Float32 DEMs at all (8-bit RGB only, no EPSG:3857, local files only, unstable flag).

**Where PostGIS does earn a place: as a batch generalization stage inside the existing DAG.** `ST_CoverageSimplify` (PostGIS 3.4+/GEOS 3.12+) simplifies a polygonal coverage so shared edges simplify identically — the partition stays gap-free by construction. That is exactly the depare contract, and exactly what tippecanoe cannot do (`--detect-shared-borders` crashes on the Stockholm fixture via the unfixed wagyu bug; the current fallback simply doesn't simplify shared nodes, costing bytes). It's a window function over the whole coverage, so it's a build step, not a serving path — which fits: pre-generalized per-zoom-tier depare feeding the existing FGB → tippecanoe path, no new serving infrastructure.

## What to actually do, ranked by leverage

1. **Measure the cell-sharded vector bundle (`b077795`) before any further surgery.** It is the architecture every alternative converges on (dirty cell rebuilds alone; the raster side already proves the shape at 239 cells/~2 min). The 18-hour run predates it. Open items the plan already names: planet tile-join wall, per-cell scratch vs disk budget, z7/z8 seam check.
2. **Replace the tile-join stitch with `pmtiles merge`.** Byte-copy merge of disjoint clustered shards; publish becomes minutes of sequential I/O — and it exits the felt/tippecanoe#278 PMTiles corruption bug. Watch: local-file inputs only, ~40 B RAM per directory entry, no cross-shard dedup (don't emit empty ocean tiles per shard), layer/attribute consistency is the pipeline's job since merge never looks inside a tile.
3. **Unlock tippecanoe's parallel read for soundings.** `-P` requires newline-delimited GeoJSON or FGB; soundings intermediates are plain `.geojson`, which is why the read phase measured ~80 minutes at 0.2 cores. Contours/depare already emit FGB. Small, contained, testable against canonical tile hashes.
4. **Run the serial vector tail on a cheap box.** Measured peak 6–9 GiB at 1–6 cores fits a CX53 (€0.047/hr) instead of the ccx63 (€1.37/hr post-reprice): terrain phase ~1h on the big box, vector phase ~7h on the small one ≈ €1.75 vs €11.7 — an ~85% build-cost cut with zero pipeline changes, using the existing R2 hydrate/push for the handoff. (The shard in item 1 may shrink the tail enough to make this moot — measure first.)
5. **Pre-simplify the depare nodata content to stem resolution.** −54% to −67% of vertices, already identified in the native-resolution plan as a Part 2 prerequisite. Bigger than any tool swap; helps every downstream option.
6. **Split the staleness keys that force false planet rebuilds** (`build.smk`): per-stage toolchain fingerprints (a tippecanoe bump must not invalidate every mosaic tile — `utils.toolchain()` currently does), scope `MASKS` to intersecting tiles, and keep `MERGE_CFG`/`version` blast radii deliberate. One documented 8h12m no-op rebuild came from exactly this class.
7. **Pre-bake overzoom leaves at build time** with `tippecanoe-overzoom`/`tile-join --overzoom` (the C++ original of the Worker's JS port) where traffic warrants, cutting Worker CPU-ms — the only real serving cost — to near zero.
8. **Prototype `ST_CoverageSimplify` on the Stockholm fixture** (124k-polygon depare stem that crashes wagyu). If it holds, add a batch coverage-generalization step per zoom tier feeding the existing bundle path. This is the escape hatch from wagyu, which is the actual single-thread pathology.
9. **Prototype `maplibre-contour` for the contour layer.** Client-side contours from the Terrarium tiles already served: deletes the 2h53m contour tippecanoe run and makes m/ft/fathom a runtime `multiplier` instead of duplicated baked geometry (proven with negative depths in the wild). Blocker to test: chart-grade treatment — Chaikin smoothing, tier gating, bias-shallow — has to move DEM-side or be accepted as lost. Complement, not replacement: no depare fills, no soundings.
10. **Spike Planetiler on one dense cell's depare** as insurance. felt/tippecanoe's last stable release is 2.79.0 (Jul 2024); the build pins an unreleased commit and works around two unfixed bugs. Planetiler's maintainer cites this exact workload (DEM contour FGB tiles that made tippecanoe fall over) as the project's motivating use case, and Overture migrated to it in April 2026. If JTS avoids the wagyu pathology, there's a proven second path.

Cheap wins surfaced along the way: felt/tippecanoe gained `--drop-by-attribute-as-needed` (Mar 2026) — drop by depth-band importance instead of geometry density; `gdal raster mosaic --pixel-function max` (GDAL 3.12+) gives a free shallow-bias audit (diff shallowest-wins vs priority-wins per pixel); LERC_ZSTD at `MAX_Z_ERROR=0.01` with a shallow pre-bias would halve the mosaic store at ~10× write speed (LERC error is symmetric — the pre-bias is what keeps charted ≤ true); Mapterhorn's `aggregation_run` is worth comparing against the vendored copy.

## What not to do

- No PostGIS raster, no Zarr-as-primary-store, no TileDB, no dynamic raster tiling, no live-DB vector serving — each fails cheap-serving, tooling, or chart-safety criteria above.
- Don't drop the Worker: it is the cache, the sparse-archive shim, and the ETag layer, at $5–6/month.
- Don't split `vector.pmtiles` per layer (standing decision, re-confirmed) — the cell shard achieves incrementality without changing the served artifact.
- Don't fan the build out to a fleet; make the one serial stage parallel instead.

Two serving footnotes for later: **Cloudflare Project Alexandria** offers recurring annual credits (Workers request increases, R2 storage, plan upgrades) to open-source projects — this project likely qualifies and it would remove the cost question entirely. And if traffic ever outgrows the Worker tier, the documented escape is **R2 + a Bunny.net pull zone** ($0.005–0.01/GB, no per-request fees — the one line item that matters for request-heavy, object-small tile traffic; Fastly and CloudFront both charge ~$0.01/10k requests).

## Context worth keeping

No precedent exists for what this project is building — the intersection of vector tiles × chart-grade depth semantics × planet scale is empty. Everything planet-scale is raster or low-zoom GEBCO polygons; everything chart-grade is per-ENC-cell and regional (tile57, s57-tiler, vectorcharts). Two schema ideas from tile57 worth stealing when convenient: parallel unit attributes on soundings (one feature, both ladders), and baking `drval1`/`drval2` + color tokens so mariner-selected safety-contour shading and day/dusk/night switching are pure style expressions. MapTiler Contours is the shipped precedent for the ft ladder (sibling layers in one tileset). The IHO S-101 Portrayal Catalogue is machine-readable Lua on GitHub, actively maintained, if bake-time chart portrayal ever becomes a goal.
